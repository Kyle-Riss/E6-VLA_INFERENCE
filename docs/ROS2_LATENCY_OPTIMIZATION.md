## 전체 그림 — 추론이 어떻게 동작하는가

로봇이 "왼쪽 박스를 집어 오른쪽에 놓아라"는 명령을 받으면 아래 순서로 동작한다.

```
① 카메라가 영상 촬영 (18Hz)
       ↓
② AI 모델이 영상을 보고 "다음 16 스텝 동안 이렇게 움직여라" 계획 생성
       ↓
③ executor가 계획을 꺼내 로봇 팔에 명령 전송 (16Hz)
       ↓
④ 로봇 팔이 실제로 움직임
```

이 흐름에서 **②→③→④ 사이에 지연**이 생기면 로봇이 물체에 도달하는 데 오래 걸리거나,
엉뚱한 방향으로 움직이다가 다시 접근하는 현상이 생긴다.

개선 전에는 박스에 도달해 흡착하기까지 **100~190초**가 걸렸고,
개선 후에는 **40~75초**로 단축되었다.

---

## 문제 1 — 로봇이 "묵은 명령"을 실행하고 있었다

### 무슨 일이 일어났는가

AI가 매 0.5초마다 새 계획(action chunk)을 만들어 보낸다.  
executor는 이 계획을 꺼내 1/16초(약 62ms)마다 로봇에 `MovJ` 명령을 하나씩 보낸다.

문제는 `MovJ`가 **줄 세우기(queue)** 방식으로 동작한다는 점이다.

> 비유: 식당 주방에 주문이 계속 들어오는데, 주방장이 오래된 주문부터 순서대로 처리한다.  
> 손님이 주문을 바꿔도 이전 주문이 먼저 나온다.

executor가 16Hz로 명령을 계속 보내면, Dobot 내부 큐에 명령이 쌓이고
로봇은 AI가 **3~4초 전에 계획한 위치**를 향해 움직이게 된다.  
AI는 현재 위치를 보고 계획을 짜는데, 로봇이 과거 명령을 실행 중이니 계속 어긋난다.

```
AI가 계획 생성 (현재 위치 기준)
  →  executor가 MovJ 명령 큐에 추가
  →  큐에 이전 명령이 쌓여 있음
  →  로봇이 2~3초 전 계획 실행
  →  AI가 보는 현재 위치 ≠ 로봇 실제 위치
  →  수렴하지 못하고 반복
```

### 어떻게 고쳤는가 — `ServoJ` 도입

`MovJ` 대신 `ServoJ`를 쓰도록 `control_mode` 파라미터를 추가했다.

`ServoJ`는 큐 없이 **지금 바로 이 위치로 가라**는 실시간 명령이다.  
이전 명령이 아직 실행 중이어도 새 target으로 즉시 갱신된다.

> 비유: 주방장에게 "지금 당장 이 요리로 바꿔라"고 말할 수 있는 방식.

```bash
# ServoJ 모드로 실행
ros2 launch e6_vla_ros e6_vla.launch.py control_mode:=servoj
```

| 모드 | 특성 |
|---|---|
| `movj` (기본) | 부드럽지만 큐 지연 발생 가능 |
| `servoj` | 큐 없음, AI 계획을 즉시 반영 |

## 문제 2 — 카메라가 그리퍼 상태를 잘못 읽고 있었다

### 무슨 일이 일어났는가

AI 모델은 매 프레임마다 **"현재 그리퍼가 켜져 있는가 꺼져 있는가"** 를 입력으로 받아야 한다.  
이 값이 틀리면 AI는 엉뚱한 판단을 하게 된다.

카메라 노드는 Dobot 하드웨어에서 `DigitalOutputs`라는 값을 직접 읽어 그리퍼 상태를 판단하고 있었다.  
그런데 실제로 흡착 명령(`ToolDO(1, on)`)을 보내도 이 값이 바뀌지 않는 버그가 있었다.

결과적으로 그리퍼 상태는 **항상 0.0(꺼짐)** 으로 고정되었고,  
`PhaseTracker`는 "아직 그리퍼가 안 켜졌으니 아직 안 잡은 것"으로 판단해  
계속 접근 동작을 반복했다.

```
실제 상황: 그리퍼 ON (흡착 중)
카메라가 읽은 값: 0.0 (꺼짐으로 오인)
AI가 받은 입력: 그리퍼=0 → "아직 안 잡았다"
결과: 다시 접근 동작 반복
```

### 어떻게 고쳤는가 — efference copy (명령 메아리)

하드웨어에서 읽는 대신, executor가 흡착 명령을 보낼 때 **동시에 ROS2 토픽으로도 알리도록** 했다.

> 비유: 내가 전등 스위치를 눌렀으면, 불을 직접 보지 않아도 "스위치를 눌렀다"는 사실 자체를 기억하는 것.

```
executor가 흡착 명령 실행
  ├─ Dobot 하드웨어에 ToolDO(1, on) 전송
  └─ ROS2 토픽 /e6/gripper/commanded = 1.0 발행

카메라 노드가 이 토픽을 구독
  └─ self._last_gripper = 1.0 으로 즉시 갱신
       └─ AI 모델 입력에 반영
```

이 방식은 뇌과학의 "efference copy(원심성 복사)" 개념과 같다.  
뇌가 팔에 명령을 보낼 때 감각 피질에도 "이런 명령을 보냈다"고 동시에 알리는 것처럼,  
executor가 로봇에 명령을 보낼 때 카메라 노드에도 동시에 알린다.

## 문제 3 — 카메라와 로봇 명령의 속도가 안 맞았다

### 무슨 일이 일어났는가

학습 데이터는 **18Hz**(1초에 18장)로 수집했다.  
모델이 예측하는 "1 프레임당 관절 이동량(delta)"은 이 속도를 기준으로 학습되었다.

만약 executor가 20Hz로 명령을 보내면 실제로는 더 빠르게 움직이고,  
16Hz로 보내면 더 느리게 움직인다. 학습 때와 속도 감각이 달라지는 것이다.

### 어떻게 맞췄는가

| 노드 | 주파수 | 이유 |
|---|---|---|
| 카메라 노드 | 18Hz | 학습 데이터 수집 주파수와 동일 |
| executor | 16Hz | 모델의 action fps와 동일 |
| 추론 호출 | 16Hz | executor와 동기화 |

## 문제 4 — AI 계획을 너무 오래 믿고 있었다

### 무슨 일이 일어났는가

AI는 한 번에 **16 스텝짜리 계획**을 만든다.  
이 계획 16개를 전부 실행하고 나서 다시 추론하면,  
그 1초 동안 AI는 로봇이 어디 있는지 보지 않는다.

물체 위치가 조금 달라도 수정을 못 하고, 계획대로만 움직이게 된다.

### 어떻게 고쳤는가 — 8 스텝마다 재추론

16개 중 앞 **8개만 실행**하고, 0.5초 후에 다시 추론해서 새 계획을 받는다.

```
추론 → 계획 16개 수신
  → 앞 8개 실행 (0.5초)
  → 다시 추론 (현재 카메라 영상 기반)
  → 앞 8개 실행 ...
```

0.5초마다 카메라를 다시 보고 계획을 수정할 수 있어서  
물체 위치가 조금 어긋나도 스스로 보정이 된다.

## 문제 5 — 오래된 계획이 남아 있으면 위험하다

정책 서버가 잠깐 끊겼다가 다시 연결되거나, 추론이 늦게 도착할 경우  
5초 이상 된 낡은 계획이 executor에 남아 있을 수 있다.

이 계획을 그대로 실행하면 로봇이 엉뚱한 곳으로 움직인다.  
5초가 지난 계획은 자동으로 버리도록 했다 (`chunk_staleness_sec=5.0`).

## 개선 전후 수치 비교

아래 표는 `inference_metrics.txt`에 기록된 실제 측정값이다.  
**"이동 시작 → suction ON 시간"** = 로봇이 움직이기 시작해서 박스를 집기까지 걸린 시간.

| 시기 | 걸린 시간 | 추론 횟수 |
|---|---|---|
| 개선 전 (v16~v17 시기) | 100~190초 | 40~78회 |
| v18/v19 모델 + 일부 개선 | 57~84초 | 24~35회 |
| 현재 (2026-06-03) | **40~75초** | **17~31회** |

추론 횟수가 곧 "AI가 몇 번 판단했는가"를 나타낸다.  
횟수가 줄었다는 것은 더 적은 판단으로 목표에 도달했다는 뜻 — 효율이 높아진 것이다.
